# 更新、Agent 升级与回滚

控制端、网页、Agent 和辅助资产需要保持可兼容关系。GitHub `main` 有新提交，不等于已经生成新的正式 Release。

## 选择更新路径

| 当前部署 | 使用方式 | 边界 |
| --- | --- | --- |
| Linux 裸机/systemd，面板正常且目标有完整发布清单 | 系统设置 → 维护 → 系统更新 | 校验资产、架构、API 协议及健康状态 |
| 旧部署或面板不可用 | 安装脚本兼容更新 | 不自动替换任意外置网页目录 |
| Docker Compose | 宿主机拉取并重建镜像 | 不在容器内部原地更新 |
| 节点 Agent | 服务管理中的升级入口/节点接入流程 | 节点需下载对应平台资产 |

## 所有更新前

1. 下载[可恢复的备份](/docs/operations/backup)。
2. 阅读目标发布说明，核对架构、数据库迁移和已知问题。
3. 记录当前版本、服务状态、网页来源及镜像/二进制信息。
4. 确认目标机器能访问下载地址且有临时磁盘空间。
5. 一次只执行一种更新路径，避免面板与命令行同时操作。

## 面板完整更新

先检查更新，核对目标发布后再安装。正式产品包依赖清单 `relaydock-release-manifest.json` 和 `checksums.txt` 等配套资产。健康检查失败会进入回滚/恢复流程，应查看最终状态，不反复点击更新。

内嵌网页随控制端二进制更新；外置网页只有使用受管的 `current -> releases/<release-id>` 布局才会参与相应事务。普通静态目录不会自动成为安全更新目标。

## 命令行兼容更新

```bash
curl -fsSL https://raw.githubusercontent.com/violetaini/relaydock/main/install.sh -o install.sh
sudo bash install.sh update
```

兼容更新保留现有路径和数据，校验下载资产；但不等同于完整产品清单/API/网页健康事务，也不会替你切换任意外置前端。完成后检查网页与后端版本。

快捷命令可用的部署也可执行 `relaydock update`。使用前确认指向当前实例，而不是同一主机上的其他安装。

## Agent 升级失败怎么查

`exit status 1` 不是根因。展开每台服务器日志，按首个错误判断：

| 错误类别 | 核对 |
| --- | --- |
| 下载超时 / TLS | 节点自身访问 GitHub 的网络、DNS、时间和证书链 |
| 404 / asset missing | 目标标签是否发布了对应 Agent 文件，版本和资产名称是否匹配 |
| Exec format error | `uname -m` 与 AMD64/ARM64 资产是否一致 |
| 校验失败 | 下载是否完整、校验清单是否同一版本；不要忽略校验强行执行 |
| Permission denied | 文件权限、目录权限、noexec、服务用户 |
| 重启后离线 | 启动参数、令牌、核心配置、端口冲突及系统日志 |

先更新一台、验收再批量；批量部分失败时保留逐台结果。安装脚本从 Release 取得资产，不能因为仓库源码已更新就认为某个旧标签已有新文件。

## 回滚步骤与边界

优先使用更新系统记录的旧二进制/网页指针或旧镜像，先保留失败日志与当前数据。只有明确数据库不兼容、且决定接受恢复点后的数据损失时，才执行数据恢复。

回退后验证登录、Agent、入站、普通用户授权、订阅以及一条实际代理链。面板首页 200 只是其中一项。

更多实现细节可查看[仓库运维手册](https://github.com/violetaini/relaydock/blob/main/docs/operations/update-runbook.md)。
