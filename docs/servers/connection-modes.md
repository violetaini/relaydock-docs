# WebSocket、Push、Pull 怎么选

三种模式描述的是**面板与 Agent 的控制连接**，不是客户端代理协议，也不是节点传输层的 WS/gRPC。

## 模式比较

| 模式 | 主要上报/采集方向 | 网络要求 | 适合场景 |
| --- | --- | --- | --- |
| WebSocket | Agent 主动连接控制端并维持通道 | Agent 能访问控制端；反代允许 WebSocket | 新部署、NAT 后主机、统一 HTTPS 入口 |
| HTTP Push | Agent 主动向控制端推送心跳、流量等数据 | Agent 能访问控制端；远端管理仍需核对 Agent HTTP 可达性 | 不使用持续 WS 的 HTTP 上报环境 |
| HTTP Pull | 控制端访问 Agent HTTP API 抓取数据 | 控制端能访问 Agent 地址/端口；Agent 也可能发送初始心跳或回退上报 | 主控可主动访问节点的环境 |

上表说明主要数据方向。远端管理可通过 WS 反向 RPC 或 HTTP 调用，因此“能推送指标”不等于所有管理操作都只需出站连接。具体握手路径、端口和令牌由当前面板生成命令决定。不要把上一版本、其他实例或其他模式的命令混用。

## WebSocket 部署顺序

1. 先确认控制端规范 HTTPS 入口可达。
2. 在服务管理选择 WebSocket，保存并重新获取接入命令。
3. 节点执行命令，确认 Agent 可解析控制端域名、验证证书。
4. 观察心跳连续稳定，检查反代是否正确返回升级响应。

若浏览器页面正常但 Agent 不在线，排查代理的 Upgrade 头、TLS 证书链、系统时间和长连接空闲超时。

## Pull 抓取与 HTTP 管理地址

Pull 抓取地址及 HTTP 管理地址可以是可达 IP 或域名。动态地址环境建议配合 DDNS，但域名必须从**控制端所在网络**解析到可达地址。测试时注意内外网 DNS、NAT 回流和云安全组。HTTP Push 的指标上报方向相反，但涉及管理操作时也要检查调用路径。

管理端口不要向全网无差别开放。业务代理端口与管理端口不同，不应将 Agent 管理接口当成客户端连接入口。

## 切换模式

先确保新方向可达，再在后台修改模式并更新 Agent 启动配置。保留原连接信息便于回退；切换后观察一个完整心跳周期以上，并测试一次远端只读状态操作。

一侧改成 Pull、另一侧仍按 Push 运行不会自动协商成兼容状态。

## 四个状态的区别

| 状态 | 说明 |
| --- | --- |
| 机器能 ping | 只能说明 ICMP 可达，且部分机器本来就禁 ping |
| Agent 在线 | 控制通道和认证已建立 |
| 核心正常 | 配置被接受且运行时未报错 |
| 客户端可用 | 业务端口、协议、凭据、出口和授权均通过 |

排错应逐层验证，不把这些状态互相替代。
