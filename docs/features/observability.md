# 探针、通知与运行状态

探针用于观察服务器，通知用于传达事件，日志用于定位原因。三者互相补充，不能用“没有告警”证明系统没有故障。

## 公开探针与后台

公开探针可以展示服务器状态和指标，后台提供管理操作。公开页面展示哪些服务器由配置决定；对外发布前检查是否暴露不必要的主机名、地址或内部信息。

伪装/探针首页与默认登录后进入后台是不同设置。不要为了改变公开首页行为而修改用户授权。

## 指标怎么读

| 指标 | 用途 | 注意 |
| --- | --- | --- |
| 最近心跳 / 在线状态 | 控制通道健康 | 不代表所有业务端口可用 |
| CPU / 内存 / 负载 | 主机资源状态 | 负载与 CPU 百分比不同 |
| 网卡收发 | 整机流量变化 | 包含代理之外的进程 |
| 节点/用户流量 | 业务使用及归因 | 依赖核心统计和用户映射 |
| 测速 / 延迟 | 特定观察点的链路表现 | 需记录测试位置和目标 |

## 配置通知

在系统设置的通知与 Telegram Bot 相关入口，按实例支持的渠道配置。先发测试通知，再验证实际事件能触发；测试成功只证明当时渠道可达，不证明所有事件都已启用。

如果使用 webhook 等外部 URL，避免指向不可信服务或回送含秘密的完整配置。

## 通知未送达

1. 确认对应事件确实发生、策略确实启用。
2. 核对接收人、频道权限及 Token。
3. 检查控制端访问外部通知服务的网络与 DNS。
4. 检查速率限制、渠道 API 错误和重试结果。
5. 对每日类通知核对控制端时区和计划时间。

## 日志使用

按时间窗口收集控制端、Agent、核心和反代日志。调试模式可能增加详细信息和磁盘占用，复现完成后及时关闭。

对外反馈时遮蔽令牌、订阅地址、密码、私钥和邮件等个人信息。保留状态码、版本、时间和错误链即可，没必要公开整份数据库。

完整取证顺序见[分层排错](/docs/operations/troubleshooting)。
