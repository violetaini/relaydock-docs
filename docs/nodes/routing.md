# 直连、转发、多跳与出站路由

这些功能都能改变流量路径，但改变的位置不同。选择前先画清楚“谁监听、谁建立下一跳、客户端使用哪套凭据”。

## 路径比较

| 方式 | 路径示例 | 改变什么 |
| --- | --- | --- |
| 普通直连节点 | 客户端 → B → 目标网络 | 客户端直连 B 的代理入站 |
| 任意门入口 | 客户端 → A → B → 目标网络 | A 透明转发到 B，客户端协议继承 B |
| 多跳转发 | 客户端 → A → C → B | 多个中继的转发路径 |
| 出站路由 | 客户端 → B → 指定 outbound → 目标网络 | B 核心根据规则选择向外连接的方式 |
| 客户端链式代理 | 客户端自行选择多个代理跳转 | 链路由客户端配置控制 |

名称里写 `Tunnel` 或标签写 `Forward` 并不会自动建立真实转发。

## 任意门适用范围

用于给已有受管物理节点增加一个入口。入口和目标应具有明确绑定，切换目标时同步远端意图与客户端配置。具体步骤见[任意门](/docs/nodes/forwarding)。

别通过 A 绑定 B、B 再绑定 A 实现多跳；循环会导致无法连接或资源消耗。

## 多跳转发规划

当前转发功能支持按界面配置多跳路径；范围和权限以该版本校验为准。每一跳都需要可达下一跳，端口范围应来自管理员授权的模板。不同主机可以使用相同端口，同一主机的同一监听地址/协议仍不能重复占用。

先验证每一段，再验证整条链：

```text
A 可访问 C:目标端口？
C 可访问 B:目标端口？
各跳 Agent 与实际监听正常？
客户端到 A 的入口可达？
```

## 出站与路由

先建立可用出站，再配置匹配规则，确认规则顺序与兜底行为。`tag` 是引用关系的重要部分：修改出站 tag 后应检查路由是否仍引用旧值。

域名匹配、IP 匹配与 DNS 解析策略会影响路由结果。先导出当前配置，在非关键节点验证；不要把所有规则一次性替换后才查问题。

## 计量与授权

多跳可能让多台服务器都产生网卡流量，不应把各机流量之和直接视为单个用户流量。转发能力授权、物理节点授权与客户端订阅范围也不是同一层，分别在对应服务授权中维护。

## 如何定位路径不符

核对客户端当前选中节点、入口监听、各跳目标、核心路由、DNS 结果和出口观察点。若仅 UI 名称正确、实际目标未保存成功，仍可能走旧路径。保留更新时间及相关日志，避免同时修改多跳导致失去依据。
